## 一、必须修正的前后矛盾（v0.1 存在的问题）

### 矛盾 1：Embedding 选型结论自相矛盾（已修正）

| 位置 | v0.1 内容 | 问题 |
|------|----------|------|
| 2.4 节 | 结论「不适用，保留 MiniLM」 | 论证不充分 |
| 第五章 | P0 任务「替换中文 Embedding（MiniLM→m3e-base）」 | 与 2.4 节矛盾 |

**修正后结论**：**采纳专家意见，替换为 m3e-base**。  
理由：
- 本系统知识库文档（医学术语解释、临床指南）以**中文为主**
- `all-MiniLM-L6-v2` 是纯英文预训练模型，对中文语义表征能力极弱
- 虽然特征名是英文（`lab_lactate`），但 RAG 检索的是**中文知识库文档**，不是特征名本身
- 即使特征名英文检索命中，后续 LLM 解释时仍需理解中文医学上下文，embedding 召回质量直接决定解释质量

## 二、v0.1 论证薄弱之处（已补充）

### 2.1 特征名可读 ≠ 无需元数据映射（已补充 feature_meta.yaml）

**专家批评**：特征名 `lab_lactate` 可读，但检索目标是「该特征异常值对应的临床意义」，而非特征名本身。例如 `shock_index` 升高，知识库写的是「休克指数 > 1.0 提示循环衰竭」，字面不完全匹配。

**项目实际**：
- 特征名确实在 `configs/features.yaml` 中定义为可读英文
- 但**单位、正常参考范围、计算口径**确实缺失集中维护
- LLM 解释时可能误读数值（如将 mmol/L 和 mg/dL 混淆）

**修正措施**：新增 `configs/feature_meta.yaml`，每个特征补充：
```yaml
lab_lactate:
  standard_name: "Lactate（乳酸）"
  unit: "mmol/L"
  normal_range: [0.5, 1.7]
  critical_high: 4.0       # 临床危急值
  description: "组织灌注不足的标志物，ICU 脓毒症筛查核心指标"

shock_index:
  standard_name: "Shock Index（休克指数）"
  unit: "次/分 ÷ mmHg"
  normal_range: [0.5, 0.7]
  critical_high: 0.9       # >0.9 提示休克
  description: "心率/收缩压比值，早期休克筛查指标"
```
成本：19 个特征 × ~5 行 = ~100 行 YAML，极低成本，收益极高。

### 2.2 MIMIC DUA 合规风险（已重写）

**v0.1 错误表述**：「MIMIC 是公开去标识化数据集，所以准标识符风险低，合规风险可忽略」

**专家批评**：混淆了两个问题——重识别风险 vs. 数据外传合规。MIMIC-IV 的 DUA 是否允许将数据传给第三方 LLM API，与"数据是否公开"是两回事。

**修正后分析**：

| 问题类型 | 本项目实际 | 风险等级 |
|---------|-----------|---------|
| 重识别风险 | 传入 LLM 的为聚合统计值（均值/最小值），非原始时间序列 | **低** |
| DUA 合规 | **待确认**——MIMIC-IV DUA 条款需逐条核对 | **中** |
| PII 外传 | 特征名 + 数值，无姓名/ID/年龄精确值 | **低** |

**修正措施**：
1. 在报告中明确标注「MIMIC DUA 合规性待确认」为待办项
2. 传入 LLM 的字段严格使用特征白名单机制（`feature_meta.yaml` 中的 `api_allowed_fields`）
3. 不在 prompt 中包含任何患者可识别信息（stay_id 仅用于内部缓存 key，不传入 LLM）

### 2.3 引用校验方法缺陷（已修正）

**v0.1 方案**：用 embedding 相似度 > 0.5 判断引用有效

**专家批评**：解释文本基于引用片段生成，天然相似度就高，无法检测「文不对题」的虚假引用。

**修正后方案**：改用**关键事实核对**：
1. 从解释文本中提取所有数值/阈值（如「乳酸 2.3 mmol/L」「正常范围 0.5-1.7」）
2. 检查对应引用片段是否包含这些数值
3. 数值匹配失败的引用标记为 `reference_valid: false`
4. 相似度校验作为辅助手段，不单独作为判断依据

### 2.4 父子 Chunk 规则不明确（已明确）

**v0.1 模糊表述**：「表格内容整体保留为一个 chunk（不过 512 字符限制）」

**专家批评**：512 字符限制和表格完整性冲突，规则不清晰。

**修正后规则**：
```
Chunk 切分策略：
1. 优先按段落/句子边界切分（SentenceSplitter，chunk_size=512，overlap=64）
2. 表格/评分标准整体作为一个 chunk，不受 512 字符限制（上限 2048 字符）
3. 超过 2048 字符的表格按行拆分，每行不超过 512 字符
4. 父子索引：子 chunk 用于检索命中，命中后返回完整父 chunk 给 LLM
   - 父 chunk = 原始段落/表格（未切分）
   - 子 chunk = 切分后的片段（用于向量检索）
```

### 2.5 降级输出未定义（已补充）

**v0.1 模糊表述**：「RAG 为空时返回原始 SHAP 值」

**专家批评**：降级输出形态不明确，体验断层。

**修正后降级策略**：

| 场景 | 降级行为 | UI 展示 |
|------|---------|---------|
| RAG 知识库为空（索引未构建） | 返回结构化解释，但 `references` 为空，`rag_available: false` | 顶部显示黄色提示：「当前无医学参考依据，以下为模型原始数值」 |
| LLM API 不可用 | 返回 SHAP 原始值 + 短文本说明（来自本地规则模板） | 显示：「AI 解释服务暂不可用，展示原始 SHAP 归因」 |
| 引用校验失败（全部无效） | 返回解释文本，但 `reference_valid: false` 标记 | 不展示引用来源，标注「暂无匹配医学依据」 |

降级输出样例（Markdown）：
```
## 风险评估解释（降级模式）

> ⚠️ 当前无医学参考依据，以下解释基于模型原始数值，仅供参考。

**风险概述**：入ICU后1小时预测未来12小时死亡风险为 18.5%（低风险）

**关键驱动因素（模型归因）**：
- 乳酸（2.3 mmol/L）：模型贡献 +0.041（正向，提示风险升高）
- GCS评分（14分）：模型贡献 -0.028（负向，提示风险降低）

**说明**：SHAP 值反映特征对模型输出的贡献方向与幅度，
不代表临床因果关系。请结合临床综合评估。
```

## 三、新增专家反馈要点（v0.1 未覆盖）

### 3.1 提示注入防护（已补充）

**v0.1 措施**：XML 标签包裹 + Prompt 声明

**专家批评**：只能挡简单注入，无法防护角色扮演绕过等复杂攻击。

**修正后措施**（三层防护）：
1. **输入层**：XML 标签包裹所有外部内容，明确标注 `<data>...</data>` 而非 `<instruction>`
2. **检测层**：对检索片段做指令关键词扫描（「忽略上述」「你现在是」「执行以下指令」等），命中则丢弃该片段
3. **输出层**：对 LLM 输出做基础合规扫描，拦截明显违规内容

### 3.2 API Key 管理底线（已补充）

**v0.1 完全豁免**：「学生项目，.env 足够」

**专家批评**：基础安全底线不应豁免。

**修正后措施**：
- 明确 `.gitignore` 中排除 `.env` 和 `configs/*.yaml`（含 API Key）
- 提供 `.env.example` 模板，填写说明
- 在 README 中添加安全提醒：「勿将 API Key 提交至 Git，勿在公开文档中展示」
- 区分开发/演示用 Key，不混用生产环境（如有）

### 3.3 FAISS 自研过滤层 vs ChromaDB 评估（已补充权衡表）

**v0.1 方案**：在 FAISS 之上自研元数据过滤层

**专家建议**：考虑直接引入 ChromaDB（底层也是 FAISS，原生支持元数据过滤）

**权衡分析**：

| 维度 | FAISS + 自研过滤 | ChromaDB |
|------|-----------------|----------|
| 额外依赖 | 无（FAISS 已用） | +1 个包（chromadb） |
| 元数据过滤 | 需自写 ~80 行代码 | 原生支持 |
| 持久化 | 需手动序列化 | 自动持久化 |
| 维护成本 | 中等（自研 bug 风险） | 低 |
| 与现有 dump 机制兼容 | 高（FAISS 索引直接序列化） | 需适配 |

**决策**：**保留 FAISS + 自研过滤层**。理由：
- 自研过滤层代码量约 50-80 行，复杂度可控
- 与现有 dump/restore 机制兼容（FAISS 索引可序列化到磁盘）
- ChromaDB 的持久化机制与本项目的 dump 文件体系需要适配，增加额外工作
- 若后续检索复杂度提升（如多路召回、重排序），可平滑迁移到 ChromaDB

### 3.4 验收标准新增：特征重要性排序一致性（已补充）

**v0.1 验收标准**：忠实度仅校验 SHAP 方向（正负）一致性

**专家补充**：仅查方向不够，LLM 可能把贡献第 4 的因素说成首要原因。

**修正后验收标准**：

| 编号 | 指标 | 计算方法 | 通过标准 |
|------|------|---------|---------|
| AC-1 | **方向忠实度** | 解释文本中特征方向（升/降风险）与 SHAP 符号一致性 | 100% |
| **AC-1b** | **排序一致性** | LLM 解释的主次顺序与 SHAP 绝对值排序一致性 | ≥ 80%（Top-3 内） |
| AC-2 | **引用事实核对** | 解释中数值是否在对应引用片段中出现 | 100% |
| AC-3 | **格式合规率** | JSON Schema 遵循率（Function Calling 强制约束后目标 100%） | ≥ 95% |
| AC-4 | **幻觉率** | 无依据陈述占比（人工标注 30 个案例） | ≤ 5% |
| AC-5 | **响应时间** | 端到端耗时（RAG 检索 + LLM 生成） | ≤ 10s（P95） |
